Three orthogonal axes

LatentGraphRAG's API factors retrieval into three independent choices:

AxisValues
corpusdocument_only · memory_only · joint_index · dual_tree
searchfull_expansion · beamdr · cross_view_beam · mmr · single_hop
fusionrrf · agreement (dual_tree only)

The core observation: the same retrieval primitive — recursive dense retrieval with multiplicative path scoring — works over documents, memories, or both. Search strategies and fusion methods then plug in independently. So instead of enumerating every (corpus, search, fusion) triple as a separate algorithm, we expose them as three orthogonal knobs.

The factoring

Think of retrieval as a product of three independent decisions:

  • corpus decides which index (or pair of indices) the search runs over.
  • search decides how the iterative retrieval expands at each hop.
  • fusion decides how two ranked lists are combined — only meaningful when corpus="dual_tree".

Mixing-and-matching gives you a clean matrix of configurations. The legacy research codebase called these "ablations 1–8"; in this package every one of those reduces to a single call.

Why this factoring matters

Search and fusion strategies are first-class plug-ins. Adding a new search strategy (say, mmr for diversity-aware expansion) means writing one module — and the dispatcher composes it with every corpus and every fusion for free. The same goes for fusion: any new fusion automatically applies to every dual-tree configuration.

You can see this matrix come alive on the Search Strategies pages, where each combination has its own animated visualization, or directly on the Combinations page.
