Why orthogonal?

Full expansion or BeamDR-style pruning can be applied over documents, memories, or both. That observation drives the whole package design — the same six search strategies, four corpus modes, and two fusion methods compose into a clean matrix of configurations rather than a long list of bespoke algorithms.

A concrete example

Four representative configurations:

ConfigurationCall
Document-Only Full Treecorpus="document_only", search="full_expansion"
Document-Only BeamDR (B=10)corpus="document_only", search="beamdr", beam_width=10
Memory-Only Full Expansioncorpus="memory_only", search="full_expansion"
Joint-Index Tree Searchcorpus="joint_index", search="full_expansion"

All four share the same retrieval primitive: iterative recursive dense retrieval with multiplicative path scoring. They differ only in which index they search and how they expand. Each is one parametric call to the same retrieve(), not a separate hardcoded routine.

What "orthogonal" actually buys

  1. Adding a new search strategy is one module. A new search (say, MMR-decoded expansion) is a single file plus a one-line entry in the dispatcher. It immediately composes with every corpus mode (document_only, memory_only, joint_index, dual_tree) and every fusion method without any extra plumbing.

  2. Adding a new fusion method is one module. Same story for fusion. RRF and document–memory agreement are siblings under latentgraphrag.fusion; a new fusion plugs in without touching search code.

  3. Adding a new corpus mode is one module. corpus/document.py, corpus/memory.py, corpus/joint.py, corpus/dual.py each handle a single concern: which index(es) the search runs over.

This decoupling is what makes the API surface stay small. The dispatcher in pipeline.retrieve() is the only place all three axes meet.
