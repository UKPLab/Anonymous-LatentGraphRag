# Relational memories

Treat every extracted (subject, relation, object) triple as a **relational memory** — a
verbalized natural-language sentence that can be retrieved with the same encoder used
for documents.

## From triples to memories

Given a chunk of text and an OpenIE pass that yields a triple `(h, r, t)`, we run an LLM
verbalizer over it:

```text
Triple: (Alice, lives in, Paris)
Sentence: Alice lives in Paris.
```

Each memory carries **provenance** — a mapping `π(m) → d` back to the source document.
This lets a dual-tree retriever project memory-level scores onto document-level rankings
before fusion.

In the package, a memory is a small dataclass:

```python title="latentgraphrag/memory/memory.py"
@dataclass(frozen=True)
class RelationalMemory:
    hash_id: str       # "memory-<md5(sentence)>"
    head: str
    relation: str
    tail: str
    sentence: str      # the verbalized form
    chunk_id: str      # provenance: which chunk produced it
    doc_id: str        # provenance: which document
```

## Why verbalize?

A naive baseline would dense-encode the raw triple string `"(Alice, lives in, Paris)"`.
This works poorly because:

1. **Encoders are trained on natural language**, not RDF tuples. They struggle to
   normalize relation strings into the right semantic neighborhood.
2. **Relational context is lost.** &quot;Alice lives in Paris&quot; carries syntactic clues
   (subject-verb-object order, English grammar) that the encoder uses.

Verbalized memories consistently outperform raw triples in our experiments.

## Template fallback

The default verbalizer uses an LLM with a single-sentence prompt:

> *&quot;You will receive RDF-style triples in the form (subject, relation, object). Write
> exactly one concise natural-language sentence that preserves the fact. Do not add extra
> facts, explanations, bullets, or formatting.&quot;*

If the LLM call fails, the verbalizer falls back to a template:

```python
sentence = f"{head} {relation} {tail}."
```

This template is also a useful zero-cost option for development or large corpora where
calling an LLM per triple is too expensive.

## Storage

Memories are stored alongside documents in the same parquet schema, but with their own
namespace and embedding index:

```text
./my_corpus/
├── memories.parquet              # hash_id, head, relation, tail, sentence, chunk_id, doc_id
└── embeddings/
    └── memories.parquet          # hash_id, embedding (float32)
```

You can also work with memories independently of the full pipeline:

```python title="memories_inspector.py"
from latentgraphrag.memory import RelationalMemory

mem = RelationalMemory.from_triple(
    ("Alice", "lives in", "Paris"),
    sentence="Alice lives in Paris.",
    chunk_id="chunk-abc123",
    doc_id="doc-456",
)
print(mem.hash_id)  # stable id deterministic from `sentence`
```

## How memories are used in retrieval

Memories show up in three of the four corpus modes:

- **`memory_only`** — search the memory index exclusively, then project scores to
  source documents at output time.
- **`joint_index`** — concatenate chunk and memory embeddings into one virtual index.
- **`dual_tree`** — search documents and memories separately, then fuse with RRF or
  document–memory agreement.

The choice depends on the task structure. Width-oriented tasks (many sub-questions, like
FanOutQA) tend to benefit from memory-only; depth-oriented tasks (MuSiQue) prefer dual
trees with agreement fusion.
