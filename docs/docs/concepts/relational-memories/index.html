Relational memories

Treat every extracted (subject, relation, object) triple as a relational memory — a verbalized natural-language sentence that can be retrieved with the same encoder used for documents.

Why verbalize?

A naive baseline would dense-encode the raw triple string "(Alice, lives in, Paris)". This works poorly because:

  1. Encoders are trained on natural language, not RDF tuples. They struggle to normalize relation strings into the right semantic neighborhood.
  2. Relational context is lost. "Alice lives in Paris" carries syntactic clues (subject-verb-object order, English grammar) that the encoder uses.

Verbalized memories consistently outperform raw triples in our experiments.

Template fallback

The default verbalizer uses an LLM with a single-sentence prompt:

"You will receive RDF-style triples in the form (subject, relation, object). Write exactly one concise natural-language sentence that preserves the fact. Do not add extra facts, explanations, bullets, or formatting."

How memories are used in retrieval

Memories show up in three of the four corpus modes:

  • memory_only — search the memory index exclusively, then project scores to source documents at output time.
  • joint_index — concatenate chunk and memory embeddings into one virtual index.
  • dual_tree — search documents and memories separately, then fuse with RRF or document–memory agreement.

The choice depends on the task structure. Width-oriented tasks (many sub-questions, like FanOutQA) tend to benefit from memory-only; depth-oriented tasks (MuSiQue) prefer dual trees with agreement fusion.
