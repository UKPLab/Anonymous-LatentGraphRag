# Why orthogonal?

Full expansion or BeamDR-style pruning can be applied over documents, memories, or
both. That observation drives the whole package design — the same six search
strategies, four corpus modes, and two fusion methods compose into a clean matrix of
configurations rather than a long list of bespoke algorithms.

## A concrete example

Four representative configurations:

| Configuration | Call |
|---------------|------|
| Document-Only Full Tree | `corpus="document_only", search="full_expansion"` |
| Document-Only BeamDR (B=10) | `corpus="document_only", search="beamdr", beam_width=10` |
| Memory-Only Full Expansion | `corpus="memory_only", search="full_expansion"` |
| Joint-Index Tree Search | `corpus="joint_index", search="full_expansion"` |

All four share the **same retrieval primitive**: iterative recursive dense retrieval
with multiplicative path scoring. They differ only in which index they search and how
they expand. Each is one parametric call to the same `retrieve()`, not a separate
hardcoded routine.

## What &quot;orthogonal&quot; actually buys

1. **Adding a new search strategy is one module.**
   A new search (say, MMR-decoded expansion) is a single file plus a one-line entry in
   the dispatcher. It immediately composes with every corpus mode (`document_only`,
   `memory_only`, `joint_index`, `dual_tree`) and every fusion method without any extra
   plumbing.

2. **Adding a new fusion method is one module.**
   Same story for fusion. RRF and document–memory agreement are siblings under
   `latentgraphrag.fusion`; a new fusion plugs in without touching search code.

3. **Adding a new corpus mode is one module.**
   `corpus/document.py`, `corpus/memory.py`, `corpus/joint.py`, `corpus/dual.py` each
   handle a single concern: which index(es) the search runs over.

This decoupling is what makes the API surface stay small. The dispatcher in
`pipeline.retrieve()` is the only place all three axes meet.

## When orthogonality &quot;leaks&quot;

Two combinations require special handling:

- **`cross_view_beam`** is a search strategy that **only makes sense** with
  `corpus="dual_tree"` because a cross-view beam queries both indices at every hop. The
  validator rejects other combinations:

```python
rag.retrieve(q, corpus="document_only", search="cross_view_beam")
# ValueError: search='cross_view_beam' requires corpus='dual_tree'.
```

- **`fusion`** is only meaningful when there are two ranked lists to fuse, i.e. with
  `corpus="dual_tree"`:

```python
rag.retrieve(q, corpus="document_only", fusion="rrf")
# ValueError: Fusion is only meaningful when corpus='dual_tree' —
#             single-view retrieval has nothing to fuse.
```

These constraints are documented in the validator and surfaced as informative errors,
not silent fall-throughs.

## Implications for the research workflow

Because the axes are independent, an ablation table generator is just a small loop:

```python title="ablation_grid.py"
results = {}
for corpus in ["document_only", "memory_only", "joint_index", "dual_tree"]:
    for search in ["full_expansion", "beamdr"]:
        # fusion only applies to dual_tree
        fusions = ["rrf", "agreement"] if corpus == "dual_tree" else [None]
        for fusion in fusions:
            results[(corpus, search, fusion)] = rag.retrieve(
                queries,
                corpus=corpus, search=search, fusion=fusion,
                k=10, max_hops=4, branching=3,
            )
```

You can sweep parameters too — `branching ∈ {1, 3, 5}`, `beam_width ∈ {5, 10, 40}`,
`gamma ∈ [-0.3, 0.9]` — without writing new code.
